# v1.1 tabular discovery and consumer delivery

This development milestone extends the reviewed semantic foundation and native
product in PRs #93–#95. It is not a release record. It neither completes the
full #72/#73 roadmap nor promotes local RT/OptiX experiments into packages.

## Why a deeper semantic model is justified now

The initial product established one owner for programs, dependencies, evidence,
selection and acceptance. Its small program vocabulary and caller-declared
centering state do not yet express a convenient train/discover/transform
workflow for a real tabular consumer. Those are current tabular requirements,
not an argument for a general compiler or a future-domain expansion.

This phase extends the same owner rather than adding a second discovery API
with its own target protocol:

- bounded proposal of interactions with training-bound frozen state;
- immutable hard predicate/region programs over raw or accepted atoms;
- multi-channel constrained selection, including an explicit Pareto frontier;
- matching train and unlabeled inference output consumed through Arrow;
- operation-specific native arithmetic across Core, CUDA, ROCm and Metal.

Python declares intent. Rust owns fit-context validation, semantic identity,
dependencies, selection and acceptance. Backend descriptors contain physical
operands and frozen constants, not semantic IDs or selection policy. Specialized
family implementations remain valid execution lowerings; they need not be
expanded into a general-purpose compiler representation.

## Fitted state, identity and reuse

`TabularSession.propose_centered_interactions()` fits each distinct eligible
atom once on an immutable discovery-role snapshot and proposes a deterministic
bounded prefix of combinations. `atoms=None` means raw sources, `arities=None`
means arity two, and `limit` is a positive upper bound (default 256). Explicit
arities must be unique and fit available atoms and the session's logical-arity
limit. Later rounds may fit combinations over explicitly accepted atoms.
The native mean follows declared row order: f32 accumulation/division for fp32,
f64 reduction followed by checked f32 freezing for mixed, and f64 throughout
for fp64. Nonfinite or overflowed fitted state is not a valid program.

Core diagnostics expose completed `fitted_mean_columns` and `fitted_mean_rows`,
separate from evidence calls and materialization/retained hits. Fitting duplicate
atom handles does not repeat a mean; fitting does not evict the session's
accepted-value cache. These are work counters, not throughput or cache-hit
formulas. GPU work counters remain explicitly unavailable.

Program identity contains mathematical operands and exact frozen constant
bits, not training/evaluation provenance. The separate Rust fitting ledger
records actual snapshot identity plus caller-declared domain/provenance. Equal
frozen programs fitted on another snapshot reuse the candidate ID while adding
an origin. Reports and accepted features snapshot transitive origins; a later
fit cannot alter earlier evidence or acceptance history. A bounded lineage
scan and expanded-record admission prevent many shared descendants from
turning a small fitting ledger into unbounded report metadata.

`fitting_origins()` exposes that history for inspection, not serialization or
proof against leakage. Report and accepted-set `evaluation_origins()` separately
include fitted contextual references from the complete evaluated evidence set,
including channels unused by the policy. Shared immutable reference snapshots
avoid candidate-by-reference metadata expansion. These references affect the
decision record, not the selected program's fitted state or later dependency
lineage. Manually declared centered constants have no automatic
training record. Marking a frame `discovery` does not certify a training split;
the application must still construct it inside the intended fold. Holdout and
inference frames cannot fit state. Transform never updates frozen constants.

`predicate(atom, relation="le"|"gt", threshold=...)` and
`decision_region(predicates)` express finite hard threshold membership using
the same registry and accepted-program lifecycle. Conjunctions flatten into
at most 64 distinct predicate terms. Logical arity counts distinct input atoms,
not bounds: `x > lo` AND `x <= hi` is unary, while its transitive source arity
can exceed one if `x` is a reused composite. Duplicate same-direction bounds,
empty/inverted intervals and ineligible operands fail closed. This supplies
frozen tabular region semantics, not learned tree induction or an RT backend
promise.

## Selection without a universal utility score

The existing primary-channel ordering and independent inclusive constraints
remain the default. An opt-in Pareto policy declares two to eight distinct
evidence channels with an explicit maximize/minimize direction for each.
Constraints first determine eligibility; a candidate is dominated only when
another eligible candidate is no worse on every objective and strictly better
on at least one. Exact equal objective vectors do not dominate one another.

The existing primary channel orders the surviving frontier, with canonical
program identity resolving ties, and the result limit truncates that order.
This is a bounded frontier selection, not a complete ordering of all dominance
layers, an optimizer over hypothetical candidates, or a weighted scalar score.
Each axis retains its original units and profile-native measured value.

Unavailable objective evidence follows the policy's `reject` or `error` rule.
An optional constraint's `ignore` setting never makes a Pareto objective
optional. Profile-quantized thresholds, immutable evaluation contexts and
accepted-feature provenance retain their existing meaning.

The frontier comparison pass has a checked worst-case bound of
`eligible_count * (eligible_count - 1) * objective_count` comparisons. It must
fit the session's `max_work` before acceptance or retention occurs. This
explicit admission policy is not a claim of subquadratic frontier complexity
or a total process-memory limit.

## Consumer acceptance, not assumed scientific efficacy

Validation must cover a real installed-package flow from training-only
discovery to train/inference Arrow matrices and a small tabular learner.
Feature order, numeric dtype, row-key alignment, frozen state, program reuse
and output lifetime are correctness contracts. Unlabeled inference must neither
evaluate evidence nor refit candidate state.

Raw-feature, labeled, target-free, paired-view and hybrid variants are separate
experimental controls. A fixture may show a mechanism or a failure mode; it
does not establish general feature quality, DL Method efficacy, superiority to
another learner, or a universal performance advantage. Consumer learning stays
outside GAFIME's feature execution engine.

## Accelerator boundary

The intended evidence matrix includes Pearson, Spearman, fixed corrected NMI
and the existing ordered graph-energy statistic. Core/CUDA/ROCm retain fp32,
mixed and fp64; Metal retains genuine fp32 only. Per-operation and fixed-bin
limits are negotiated explicitly, including Metal's supported histogram sizes.
Missing kernels or capabilities must reject before dispatch, never run hidden
Core arithmetic. Semantic `auto` retains its conservative Core policy.

Standard ABI 1.0 and generic numeric-route ABI 1.1 remain unchanged. The optional
semantic arithmetic table may evolve through reviewed append-only structures
with exact resource forecasts. This table is not a serialization ABI, a Feature
IR interchange format, or a second backend-owned semantic representation.

Source compilation, package validation, physical execution and performance
measurements are distinct evidence classes. The final PR must record which
class exists for each backend and bind it to the actual source and binaries.

The installed-package diagnostic
[`semantic_02_discovery_sanity.py`](../tests/release_measure/semantic_02_discovery_sanity.py)
records short raw samples for fitting, cold/accepted-resident evidence,
acceptance and unlabeled Arrow delivery. It checks identical evidence across
retention modes and records the source commit, extension/payload hashes and
actual Core work counters where available. Run it outside the checkout using
a release-built wheel, with explicit `--backend` and `--precision`; GPU runs
require their exact staged payload paths. It rejects a dirty tracked tree.
These bounded, potentially desktop-shared samples are overhead diagnostics,
not a physical-isolation certificate or general throughput comparison.

## Separate later experiment

Only after this product PR is established will a separate stacked experimental
PR assess local RT batch execution of mathematically eligible frozen regions.
Ordinary Core/CUDA remain the reference and performance competitors. Predicate
semantics are justified by tabular discovery independently of RT eligibility;
RT is a possible execution method, not a new feature meaning or learning mode.

RT source/runtime/artifact exclusion remains governed by the existing release
contract. No RT distribution, default dispatch, release promotion, full compiler
frontend, CV/NLP expansion, learned encoder, multi-device scheduler or Polars 2
migration is authorized by this development record.
