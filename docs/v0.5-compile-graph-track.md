# GAFIME v0.5 Compile Graph Track (Part 6)

Status of the `CompileFlags(graph=True)` execution-graph track across backends.
Graph capture is opt-in and **must never** affect `plan=True, graph=False`; every
backend falls back to normal launches when capture is unavailable.

## What graph capture does here

The resident continuous session (`ResidentContinuousMatrixSession`) keeps the
feature matrix on the device and launches one stats kernel per
`(arity, batch_size)` shape. The graph layer captures `(stats memset -> kernel)`
for a shape into an executable graph and **replays** it on later calls, with the
combo indices and the target `y` refreshed in place at stable device pointers.
The intended payoff is the permutation/stability phases, where only `y` changes
across many same-shape launches.

Graph state lives in a side table keyed by the matrix handle (additive); the
matrix structs and existing launch/free functions are untouched.

## Measured benefit (be honest)

On the RTX 4060, replaying a captured graph vs. a plain resident launch at
per-`score_combos` granularity is **neutral** (≈0.084 ms either way for small
shapes). Reason: each scored call still pays a host `cudaStreamSynchronize` plus
two H2D/D2H copies that dominate the few microseconds of launch overhead the
graph removes. This matches the plan's own assumption ("compact descriptors /
graph are for launch density, not the main kernel math speedup") and the kernel
profiles (the continuous kernel is compute-bound at ~87% SM, not launch-bound).

The real win is latent and requires the **session integration** to:
1. keep `y` resident and update it in place per permutation
   (`update_resident_target` / `gafime_*_matrix_update_target` are provided), and
2. ideally capture the whole multi-arity sweep into one graph and replay it with
   a single sync per permutation, instead of one sync per shape.

Both are session-loop changes (Part 2/4 territory) that the graph primitives here
are designed to plug into.

## Metal feasibility conclusion

Metal has no direct equivalent of CUDA/HIP stream-capture graphs. The analogous
optimizations are `MTLIndirectCommandBuffer` (ICB) or reusing a pre-encoded
`MTLCommandBuffer`. Those are a materially different execution model and only pay
off when CPU-side encoding dominates many tiny dispatches. Given (a) the measured
per-call benefit is marginal even on CUDA, (b) Metal's value would be encode
reuse rather than graph replay, and (c) no Apple-Silicon hardware is available to
validate, v0.5 keeps `graph=True` on Metal as an explicit unsupported warning
("Metal graph=True is unsupported in v0.5; using normal command-buffer
launches.") rather than shipping an unvalidated ICB path. Revisit if encode
overhead is shown to dominate a real Metal workload.
