# v1.1 tabular semantic product

> Development contract, stacked on the Core foundation in PR #93. This is not
> a released capability matrix, activation of the full #72/#73 roadmap, or a
> change to the isolated v1.0 stabilization branch.

## Architecture decision

The maintainer has authorized a bounded product milestone: one candidate,
evidence, selection and accepted-program lifecycle for tabular workflows.
Learning paradigm describes the **evaluation**, not the execution engine.

| Workflow | Evidence inputs | Selection |
| --- | --- | --- |
| Supervised | Actual, optionally partial, row-keyed labels | Explicit labeled association and constraints |
| Target-free | Reference features or caller-supplied graph | Explicit redundancy/smoothness question, not universal quality |
| Paired/self-supervised | Aligned views of the same rows | Same frozen program on both views; explicit consistency question |
| Hybrid | Several of the above simultaneously | One named primary in its own units plus independent constraints |

No mode manufactures labels, averages unrelated metrics into a universal score,
or changes candidate identity when labels or evaluation context change. A
threshold policy is not advertised as a Pareto optimizer. Arbitrary objectives,
learned encoders, resampling inference and compiler syntax are not implied.

## Public boundary

`gafime.semantic` is the additive declaration namespace. A `TabularSession`
uses the existing `EngineConfig` backend/precision intent and explicit bounded
discovery resources. Existing supervised `analyze`/`compile` behavior remains
unchanged. The new lifecycle does not implicitly consume their metric,
permutation, family-generation or ranking defaults: evidence and policy are
declared explicitly.

- Inputs become immutable Rust-owned snapshots with schema, selected numeric
  profile, ordered unique row keys, row domain, role and provenance. Mutation of
  a caller's NumPy/Arrow/Polars object afterward cannot change a snapshot.
- Labels and graphs bind by row keys to a particular snapshot. Missing labels
  are absent evidence, not zero labels. Provenance and split declarations are
  caller assertions, not a proof of statistical independence or leakage safety.
- Candidate handles are opaque and session-local. They are not integer IDs,
  hashes, serialized programs or a commitment to a future compiler IR.
- Manual declarations and bounded built-in proposal use the same Rust registry.
  Source, absolute difference, softsign and ordered frozen centered product
  remain the initial mathematical vocabulary. Centering constants are declared,
  never fitted again on inference rows.
- Evidence definitions are separate from immutable contextual bindings. Rebind
  the same question to new operands; retain old observations unchanged.
- Selection is a named maximize/minimize primary, inclusive per-channel bounds,
  explicit unavailable-value handling and deterministic identity ties.
- Accepted programs are supplied explicitly as atoms for later discovery
  rounds, as one accepted set or a bounded union of independently accepted sets.
  Raw candidate handles cannot manufacture acceptance authority.
  Inference takes only an input snapshot and accepted programs, never
  labels or a new selection policy.
- Calls are synchronous and thread-affine. `close()` is terminal and
  idempotent. Public output buffers own their Arrow memory independently of
  session lifetime. This phase promises neither asynchronous execution nor
  cross-process persistence.

Python performs declaration/import only. Rust validates and plans candidate
work, gathers contextual operands, applies policy, owns lifecycle and exports
tables. Native execution owns row-scaled arithmetic. No Python callback or
candidate/row/sample execution loop is admitted.

## Evidence contract

An association is one estimator applied to one contextual operand, rather than
one target protocol per learning paradigm. The context is a reference program,
an aligned view, or an actual labeled subset. The estimator and its parameters
participate in the immutable evidence specification; particular labels/views
do not participate in candidate identity.

| Estimator | Reference / labels | Paired view | Important boundary |
| --- | --- | --- | --- |
| Pearson | Absolute correlation | Signed correlation | Constant or degenerate operands are unavailable, not independence |
| Spearman | Absolute average-tie rank correlation | Signed average-tie rank correlation | Uses the existing native rank/Pearson primitives |
| Fixed corrected NMI | Nonlinear dependence | Nonlinear dependence, **not invariance** | Explicit fixed bins, not the legacy adaptive-MI maximum |
| Weighted graph energy | Separate graph context | Not applicable | Uncentered, translation-sensitive ratio; not a centered Laplacian score |

Fixed NMI uses equal-width bins and the existing corrected native histogram
estimator: subtract `(active_x - 1) * (active_y - 1) / (2 * support)` from mutual
information, clamp at zero, then divide by `log(min(active_x, active_y))`.
Supported bin counts are `2, 4, 8, 12, 16, 24, 32, 48, 64, 96`; admission requires
at least `8 * bins * bins` aligned samples. Insufficient density, constant input,
collapsed active bins and nonfinite arithmetic have explicit unavailable states.
A measured zero remains a measured zero. This is not a calibrated p-value.

The selected profile governs pointwise storage, reductions and public results:
fp32 remains fp32; mixed bins/materializes in fp32 and reduces in fp64; fp64 has
no fp32 intermediary. Fixed-bin parameters and estimator/context kind cannot
change through rebinding. A new estimator is a new evidence specification.

The existing supervised R² path remains supported unchanged. Adding its current
single-feature squared-correlation statistic as another semantic channel would
not add an independent ordering beyond absolute Pearson; it is not duplicated
here. Existing target-specific permutation/bootstrap algorithms likewise remain
legal supervised lowerings. They are not silently relabeled as graph/view
significance: those uses need an explicit exchangeability/resampling contract.

Multi-channel policy retains separate units: one maximize/minimize primary,
inclusive constraints and explicit missing-value behavior. Users can perform
repeated bound-constrained discovery or re-evaluate the same programs in other
contexts without conflating their measurements. This is not a Pareto-front
algorithm or a universal scalar quality score.

## Lifecycle and resource boundaries

The public session takes bounded indexed declarations, not arbitrary generators
or Python callbacks. NumPy buffers and one Arrow record batch are copied once
into immutable Rust-owned columns; row keys are explicit and unique. Buffer
ingest currently uses a contiguous temporary before column ownership, while
Arrow output intentionally copies into independently owned export arrays. These
boundary copies must not be confused with candidate recomputation.

Within execution, dependency materialization shares source/retained columns and
uses native candidate-level scheduling. Accepted values are retained only for
their exact frame; accepted **programs** may execute on new unlabeled frames.
Single-row inference is valid even though discovery/evidence frames require at
least two rows. Inference-role frames cannot be evaluated to mint new acceptance
records. Changing frame, schema, role or contextual binding does not
silently reuse old evidence. Advancing a discovery round invalidates earlier
tables for new acceptance while retaining previously accepted program authority.

Session limits cover numerical working/retained storage and bounded structural
work, not total process RSS. Caller-owned snapshots, reports and exported outputs
remain separately owned. A caller retaining every report also retains those
reports' resources; `close()` cannot revoke independently owned outputs. Native
retention/download hooks must account for actual storage and transient peaks,
not merely the logical number of selected features.

## Native lowering decision

The existing ABI 1.1 operation table is target-scoring-oriented. It cannot
represent general paired operands, graph context or reusable output columns.
Reusing its target slot as a reference/view would repeat the rejected PR #92
bridge. A genuine accelerator product needs a narrow **additive typed primitive
boundary**, not another semantic representation or a second complete engine.

Any such extension must preserve the frozen ABI 1.0 and complete ten-operation
ABI 1.1 table. Rust resolves opaque program identities to validated arithmetic
operands; launchers receive only typed operation descriptors and own device
resources. No semantic IDs, evidence provenance, selection or discovery policy
crosses into native launchers. Old payloads remain usable for old supervised
operations and explicitly unsupported for the new operation set.

Core productization and accelerator lowerings are reviewable stacked work.
Until an operation/profile/payload path is implemented and validated, it is
unsupported. `auto` must consider operation support before ranking devices and
must report the backend that actually executes. Compilation or device discovery
is never recorded as physical execution.

## Migration and validation

PR #93 remains the canonical Core foundation. Its extracted supervised
shortlist/comparison policy stays canonical; specialized family planners,
combination descriptors and statistical kernels remain legal lowerings. This
product API does not build a competing catalog, redefine targets, or import
the closed PR #92 implementation.

Admission requires public multi-round supervised, target-free, paired and hybrid
tests, independent arithmetic oracles, opaque-owner/context/schema/resource
failures, immutable-input and Arrow-output lifetime tests, precision and
worker-determinism evidence, installed supervised regression, MSRV/release Rust,
format/Clippy, architecture/package gates and exact-head independent review.
Performance observations must be bounded lifecycle/copy/reuse diagnostics, not
general speed claims. Exact-head results and remaining support gaps belong in
the draft PR and the implementation sections added as work completes.

Full Feature IR/compiler, Python feature frontend, serialization ABI, arbitrary
encoders/objectives, CV/NLP, RT/OptiX, Polars 2 and multi-device scheduling remain
outside this milestone. Neither #72 nor #73 is declared complete.
