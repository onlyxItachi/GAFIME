# v0.4.7 Distribution vs Current Kernel-Hardening Benchmark

Date: 2026-07-10

This benchmark compares the published GAFIME v0.4.7 split distributions with
commit `23da6ca3eedf4e09dde02d1154f4b2c131736515` on
`codex/cuda-hip-kernel-hardening`. It measures the installed top-level Python
API, not a direct kernel microbenchmark.

## Result

For Pearson plus R2, the current default resident analyze path is faster on all
nine ratio-bearing workloads, including the ROCm house_16H arity-2 fallback,
by `1.319x..2.100x`. Explicit compiled replay is faster by
`2.335x..7.355x`. Candidate identity matched exactly, top-20 overlap was
`20/20`, and absolute metric differences stayed below `3.64e-6`.

The main regression is explicit cache-disabled execution. It rebuilds the plan,
native handle, buffers, and uploads on every call. It is slower in eight of
nine ratio-bearing workloads, including `6.1x..11.6x` slower than v0.4.7 on
CUDA. This is an orchestration/residency gap, not a resident-kernel gap: the
same current build is up to `7.355x` faster through compiled replay.

## Packages And Hardware

The baseline environment installed all three exact split packages:

- `gafime==0.4.7`
- `gafime-cuda==0.4.7`
- `gafime-rocm==0.4.7`

The current environment installed a freshly built `gafime==1.0.0a0` wheel and
loaded the branch CUDA and ROCm payloads through `GAFIME_CUDA_V1_LIB` and
`GAFIME_ROCM_V1_LIB`.

Both isolated environments used Python 3.12.13, NumPy 2.4.6, and
scikit-learn 1.8.0 on Linux 7.0.0-27 with glibc 2.43. The CPU governor was
`performance`.

| component | hardware |
|---|---|
| Core | AMD Ryzen AI 9 HX 370, 12 cores / 24 threads |
| CUDA | NVIDIA GeForce RTX 4060 Laptop GPU, 24 SMs, `sm_89` |
| ROCm | Radeon 890M-class integrated GPU, `gfx1150`, 16 CUs, wave32, shared system memory |

CUDA was rerun after ten consecutive `0..2%` SM samples once LM Studio
inference stopped. A previously loaded model was still resident at the start
and later unloaded. Desktop GPU traffic remained, so CUDA ratios are valid as
an interleaved local A/B but are not display-free release evidence. ROCm idle
checks remained at zero activity before its formal runs.

## Workloads

Preprocessing converted numeric data to finite contiguous float32 arrays,
median-filled non-finite values, and z-scored each column outside the timed
region.

| dataset | source | rows | features | candidates, arity 1..3 | candidate-row pairs |
|---|---|---:|---:|---:|---:|
| Friedman1 | `sklearn.make_friedman1`, seed 7 | 32,768 | 24 | 2,324 | 76,152,832 |
| cpu_act | OpenML 197 v1 | 8,192 | 21 | 1,561 | 12,787,712 |
| house_16H | OpenML 574 v1 | 22,784 | 16 | 696 | 15,857,664 |

The strict contract used Pearson and R2, the same ordered candidate set, Python
list input, and full result materialization. List input is intentional:
v0.4.7 GPU distributions segfaulted on direct NumPy input, and v0.4.7 Core
direct NumPy input reproduced exit code 139 on this host. Current GAFIME accepts
the NumPy input, but using it only for current would change the API boundary
being timed.

Each cell pools 15 timed calls: three fresh processes, five repeats per
process, with process order rotated among v0.4.7, current cache-disabled, and
current default-cache variants. The first call is recorded separately and is
not in the repeated median. `compiled` is replay time after a separately
recorded compile. Current `cache=2` is the shipped default analyze-cache
capacity; `cache=0` is an explicit diagnostic mode.

Speedup below is `v0.4.7 time / current time`; values above one favor current.
Times include top-level API return plus forced materialization of every
candidate and metric.

## Spearman

Spearman used a deterministic 1,024-row cpu_act subset, arity 1..2, 231
candidates, and 236,544 candidate-row pairs. The score contract matches across
releases even though v0.4.7 completes GPU Spearman on the host and current uses
the device path. All backends retained `20/20` top-20 overlap, rank correlation
of approximately one, and maximum absolute delta `5.55e-6`.

| backend | v0.4.7 ms | current cache=0 ms (x) | current cache=2 ms (x) | compiled ms (x) |
|---|---:|---:|---:|---:|
| Core | 18.762 | 6.565 (`2.858x`) | 5.296 (`3.543x`) | 3.646 (`5.146x`) |
| CUDA | 21.576 | 147.879 (`0.146x`) | 15.469 (`1.395x`) | 14.271 (`1.512x`) |
| ROCm | 17.858 | 18.216 (`0.980x`) | 12.770 (`1.398x`) | 11.879 (`1.503x`) |

The v0.4.7 samples are bimodal (`3.88..30.48` ms on Core and
`4.80..33.33` ms on CUDA), so these pooled medians should not be treated as a
low-variance microbenchmark. Current Spearman remains an algorithmic hotspot:
its average-tie rank construction performs pairwise sample comparisons, so the
1,024-row result does not prove favorable large-row scaling.

## Mutual Information

MI results are split by estimator. The harness records the effective estimator
and refuses a strict comparison when they differ.

Core compares the same adaptive-quantile estimator on full cpu_act:

| v0.4.7 ms | current cache=0 ms (x) | current cache=2 ms (x) | compiled ms (x) |
|---:|---:|---:|---:|
| 111.222 | 123.571 (`0.900x`) | 113.986 (`0.976x`) | 106.227 (`1.047x`) |

Core MI retained `20/20` top-20 overlap, rank correlation
`0.999999987`, and maximum absolute delta `3.43e-4`. There is no meaningful
default adaptive-CPU MI speedup yet.

On CUDA and ROCm, v0.4.7 reports host adaptive-quantile MI while current runs
the fixed-bin device approximation with the sample-selected template. These
times show an end-to-end capability change, not numerical estimator parity:

| backend | v0.4.7 host-adaptive ms | current fixed cache=0 ms | current fixed cache=2 ms | current fixed compiled ms |
|---|---:|---:|---:|---:|
| CUDA | 120.562 | 146.613 (`0.822x`) | 10.299 (`11.706x`) | 6.267 (`19.237x`) |
| ROCm | 113.136 | 32.028 (`3.532x`) | 14.429 (`7.841x`) | 10.384 (`10.895x`) |

## Conclusions And Remaining Gaps

1. Resident kernels and replay are materially ahead of v0.4.7. The strongest
   strict gains are compiled house_16H (`4.890x` CUDA and `7.355x` ROCm
   arity-2); default cached gains are consistently positive.
2. Fresh uncached setup dominates short and medium GPU jobs. Reducing repeated
   plan construction, allocation, upload, and teardown is the highest-value
   end-to-end performance follow-up.
3. GPU fixed-bin MI now provides real device throughput, but it is an explicit
   approximation and must not silently replace adaptive-quantile semantics in
   correctness reports.
4. Adaptive CPU MI is approximately flat, and Spearman still has quadratic
   sample-ranking work. Those are the remaining metric-kernel targets.
5. Current fixed-bin GPU MI and strict Pearson/R2 were stable on `gfx1150`,
   while v0.4.7 ROCm showed code `-4` reliability failures at the tested
   shapes.
6. This run reaches 76.2 million candidate-row evaluations but only 2,324
   candidate equations. It does not establish 100-million-candidate planner,
   bounded-report, or device-memory behavior; that requires a separate wide,
   compact-output candidate-scale gate.

## Reproduction

The harness and dataset preparation are in
`tests/release_measure/perf_08_v047_distribution_ab.py`. Raw local JSON is
written below `build/v047-ab/results/` and remains intentionally ignored.

```bash
python tests/release_measure/perf_08_v047_distribution_ab.py \
  prepare --output-dir build/v047-ab/data

<isolated-python> tests/release_measure/perf_08_v047_distribution_ab.py \
  worker --dataset build/v047-ab/data/openml_cpu_act_197.npz \
  --backend cuda --metrics pearson r2 --input-format lists \
  --max-arity 3 --repeats 5 --cache-size 0 --include-compiled \
  --output build/v047-ab/results/example.json

python tests/release_measure/perf_08_v047_distribution_ab.py \
  aggregate --inputs run0.json run1.json run2.json \
  --output aggregate.json
```
