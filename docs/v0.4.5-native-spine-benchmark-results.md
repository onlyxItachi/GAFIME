# GAFIME v0.4.5 Native Spine Benchmark Results

These measurements compare source-built `v0.4.1` and the local `v0.4.5`
release candidate using the same public-API benchmark script:

```bash
python tests/benchmark_v045_native_spine.py \
  --n-samples <rows> \
  --n-features <features> \
  --max-comb-size 5 \
  --backends cpu,cuda
```

The benchmark uses `GafimeEngine.analyze` with report metrics
`("pearson", "r2")`, `num_repeats=1`, and `permutation_tests=0`. It is an
end-to-end Engine measurement, not a raw kernel-only microbenchmark.
This is the CUDA/CPU performance benchmark for the native-spine architecture;
it is separate from the installed-wheel GitHub runner smoke benchmark, because
the GitHub-hosted wheel runners used for this release do not expose CUDA
devices.

Local hardware:

- GPU: NVIDIA GeForce RTX 4060 Laptop GPU, SM 8.9, 8 GB class VRAM
- CUDA path: native CUDA backend
- CPU path: C++ Core backend
- Python for v0.4.5 local candidate: project `.venv`
- Python for v0.4.1 comparison: isolated `/tmp/gafime-v041-venv`

## Results

| Workload | Backend | v0.4.1 | v0.4.5 | Result |
|---|---:|---:|---:|---|
| 8,192 rows, 12 features, 1,585 interactions | CPU/Core | 0.0289 s | 0.0098 s | ~2.9x faster |
| 8,192 rows, 12 features, 1,585 interactions | CUDA | 0.2644 s | 0.1762 s | ~1.5x faster |
| 32,768 rows, 24 features, 55,454 interactions | CPU/Core | 0.5069 s | 0.5082 s | effectively unchanged |
| 32,768 rows, 24 features, 55,454 interactions | CUDA | 11.8308 s | 0.6363 s | ~18.6x faster |
| 131,072 rows, 24 features, 55,454 interactions | CPU/Core | 7.4427 s | 3.0983 s | ~2.4x faster |
| 131,072 rows, 24 features, 55,454 interactions | CUDA | MemoryError, 27.1 GiB allocation | 0.8484 s | workload now completes |

The top interaction in every successful run matched the planted five-feature
signal family. Minor ordering differences inside the same feature set are
expected because the benchmark ranks equivalent permutations by metric score and
backend numeric path.

## Interpretation

v0.4.5 changes the CUDA execution shape. The old path could materialize large
intermediate candidate arrays; the native-spine path keeps a column-major device
matrix resident and launches homogeneous arity batches with global feature-index
descriptors. That is why the larger CUDA workload moves from either seconds of
orchestration overhead or outright allocation failure to sub-second completion.

The C++ Core backend also benefits from the native fp32 buffer contract and the
single `score_combos_buffer` API. Small and large CPU workloads improve, while
the mid-size workload is roughly unchanged because the v0.4.1 C++ Core path was
already efficient for that shape.

Small interaction-count workloads can still favor CPU because the GPU launch
and orchestration overhead can dominate the math. The CUDA change in v0.4.5 is
about scaling behavior and memory shape: the mid-size workload is much faster,
and the large workload no longer materializes the 27.1 GiB candidate matrix
that made v0.4.1 fail.

These numbers are local development measurements. Users should rerun the
benchmark on their own hardware when comparing CPU/GPU crossover points.
