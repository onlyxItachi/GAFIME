# GAFIME v1.0.0-rc.2 — Validation And Artifact Identity Hardening

RC2 is a bounded hardening candidate for the established GAFIME v1 runtime.
Repository/Cargo identity: `1.0.0-rc.2`; canonical tag and GitHub Release:
`v1.0.0-rc.2`; Python/PyPI identity: `1.0.0rc2`. Publication state and operational
gates are recorded in [STATUS.md](STATUS.md) and the canonical GitHub Releases;
this note does not independently authorize publication.

## Changes Since RC1

- The advanced compatibility `BatchScheduler` rejects zero capacity with a
  clear `ValueError`, and large positive capacities cannot overflow its size
  hints.
- Shared typed-buffer ABI validation inspects the version/size header before
  reading an accepted prefix. Complete ABI 1.1 prefixes and compatible additive
  tails remain supported without changing the ABI layout.
- Generated pipeline guidance encodes dataset paths and target-column names
  as Python data literals.
- Benchmark wheel/runtime identity checks verify claimed member hashes against
  archive bytes and reject ambiguous installation destinations. Synthetic
  comparison fixtures use deterministic ZIP metadata.
- Manual Core benchmark dispatch validates the live repository-owned PR source
  before checkout, with the existing later checks retained.
- Resident NumPy analysis stages private immutable input bytes so content
  fingerprints, native ingest, and target replacement cannot diverge after a
  caller-side write. Acquisition is not an atomic transaction with an external
  writer; the lifecycle guide documents that limit and the cache-hit copy cost.
- Host C++ ABI validation fixtures use C++23; external C integration fixtures
  remain C11. CUDA payloads retain the documented C++20 compiler requirement.
- Polars stays on `polars>=1.3,<2`; migration to Polars 2 belongs to later
  v1.1/v1.2 work rather than the v1.0 stabilization scope.
- Protected candidate branches separate bounded stabilization from mainline
  development. Build, admission, tag, and publication remain bound to one exact
  reviewed release tip and its immutable frozen bytes.

The supported public API, numerical profiles, execution ownership, and package
topology remain those established by [RC1](v1.0.0-rc.1.md). No new feature family,
precision package, standalone Metal package, or RT/OptiX distribution is added.

## Runtime And Distribution Contract

Python remains the public declaration/reporting boundary; Rust owns validation,
planning, lifecycle, backend selection, and candidate-level Rayon execution
with per-candidate SIMD/native arithmetic. CUDA, ROCm/HIP, and Metal own their
respective device execution. ABI 1.0 stays frozen; ABI 1.1 remains the generic
typed-buffer/numeric-route boundary, with additive compatibility fixtures.

Core (`gafime`), CUDA (`gafime-cuda`), and ROCm (`gafime-rocm`) carry `fp32`,
default `mixed`, and `fp64`. Metal is embedded only in macOS arm64 Core wheels,
supports fp32, and rejects explicit mixed/fp64 requests. Core does not depend
on a vendor payload; each payload requires exactly matching Core. Dedicated
CPython 3.10–3.14 wheels and platform coverage remain manifest-derived.
CUDA requires the system runtime; ROCm stays thin/system-runtime, with raw Linux
wheels on GitHub and its matching source distribution on PyPI. RT/OptiX stays
experimental, local-only, and excluded from all release artifacts.

The [authoritative v1 API reference](../notebooks/gafime_v1_api_reference.ipynb)
and [public API coverage](../public-api-coverage.md) remain the user-facing
reference for supported APIs and lifecycle behavior.

## Qualification And Claim Boundaries

Local regression tests and independent patch reviews establish bounded fix
evidence, not frozen-wheel or physical-backend approval. Publication requires
exact-candidate hosted checks and standard security qualification, frozen-bundle
provenance/checksums/composition, and exact-artifact backend execution under the
[release operations runbook](release-operations.md). Retained qualification
records must identify the source and artifacts actually tested.

The completed deep security review is evidence for its original source
checkpoint. Finding disposition and regression evidence accompany the
hardening work; they do not certify a later candidate as vulnerability-free.
The established [security policy](../../SECURITY.md) and historical
[pre-RC baseline](../security/pre-rc-baseline.md) remain in force. Detailed
finding material stays private. No universal throughput, comparative GPU
performance, or security guarantee is claimed. Stable qualification and the
permanent benchmark architecture tracked by issue #71 remain separate work;
the low-copy ownership protocol tracked by issue #100 is not shipped here.
