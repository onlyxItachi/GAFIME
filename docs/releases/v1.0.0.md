# GAFIME v1.0.0 (Current Release-Preparation Notes)

> This is the current v1 release documentation bundle used for PR-level review and
> release-alignment discussion.

## V1 Release Validation Policy

The v1 release gate is driven by policy and runtime-surface checks, not
per-card micro-benchmarks or speculative per-device autotune:

- `docs/contract.md`, `CLAUDE.md`, `AGENT.md`, and `.github/workflows/v1_contract_validation.yml`
  must remain present and coherent for every v1 contract edit.
- The `V1 Contract Validation` workflow in
  `.github/workflows/v1_contract_validation.yml` must pass on supported branches.
  The Ubuntu contract gate currently runs:
  - `python tests/release_measure/contract_00_policy_files.py`
  - `python tests/release_measure/v1_architecture_gate.py --skip-cargo`
  - `python tests/release_measure/contract_01_top_level_numpy_parity.py`
  - `python tests/release_measure/contract_02_feature_generation_reference.py`
- The same workflow also runs the macOS contract check job:
  - Metal shader compilation (`metal` -> `metallib`)
  - Metal payload CMake build
  - Installed-package API validation (`GAFIME_METAL_V1_LIB` /
    `GAFIME_METAL_V1_METALLIB`)
  - `pytest -q tests/python/test_v1_metal.py`
  - `python tests/release_measure/contract_03_family_metric_backend_surface.py`

`v1_contract_validation` is intended to protect both policy coherence and
backend-surface behavior before release merge.

## Backend Selection Semantics (v1)

`backend="auto"` is a ranked resolver with current v1 ordering:

1. usable GPU candidates (`cuda`, `rocm`/`hip`, `metal`) whose C ABI loads and
   `gafime_gpu_device_info` succeeds for `device_id`
2. Rust vector ISA CPU path (`AVX512 > AVX2 > SSE4.2/NEON`)
3. Rust scalar CPU

Explicit backend requests (`cuda`, `rocm`/`hip`, `metal`) are non-fallbacking and
must fail clearly when the requested backend is unavailable or unusable for the
requested device.

Candidate-family routing is now document-aligned with v1:

- `continuous` features/interactions use native v1 expansion and scoring on
  CPU/CUDA/ROCm/Metal as allowed by installed payloads.
- `time_series` features use Rust-native CPU expansion with no Python candidate
  loop; the expanded continuous matrix is scored on CPU/CUDA/ROCm/Metal as
  allowed by installed payloads.
- `decision_path` features use Rust-native CPU decision-tree split/region
  expansion with no Python candidate loop; the expanded continuous matrix is
  scored on CPU/CUDA/ROCm/Metal as allowed by installed payloads.

No fallback to a different backend family implementation is performed under an
explicit backend request.

Metric-estimator semantics are explicit:

- Default CPU `mutual_info` uses adaptive quantile bins.
- CUDA/ROCm/Metal `mutual_info` uses the fixed equal-width-bin estimator.
- CPU/GPU MI parity is validated through `EngineConfig(mi_approximate=True)`,
  which makes the CPU use the same fixed-bin estimator as the GPU payloads.

## Distribution and Payload State

- Base package: `gafime` remains the API/orchestrator package and includes no CUDA/ROCm payload binaries in wheel artifacts.
- Split payload packages remain:
  - `gafime-cuda` for CUDA payloads
  - `gafime-rocm` for ROCm/HIP payloads
- `gafime[cuda]` and `gafime[rocm]` remain convenience install selectors for the
  corresponding payload lane.
- Metal does not have a standalone PyPI payload package in v1; it is validated as
  part of the macOS contract workflow through direct shader/payload build and
  installed-package API validation.
- Windows ROCm packaging remains gated by CI SDK-repeatability and is handled by
  platform gating.

## Integration Protocol

- Arrow C Data / Arrow C Stream is the v1 framework-integration protocol.
- Legacy DLPack / native-buffer export paths are intentionally not preserved as a
  compatibility fallback.

## Non-scope for this v1 note

The RT-core work remains on a separate feature track and is not part of the v1
release-note set.
