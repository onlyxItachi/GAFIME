# GAFIME v1.0.0b0 Beta Release

`v1.0.0b0` is the second public prerelease of the GAFIME v1 native runtime
and split backend distribution. It keeps the `v1.0.0a0` execution architecture
and hardens numerical failure handling, wide-range covariance, precision
disclosure, and ROCm artifact policy.

## Changes Since v1.0.0a0

- Correlation finalization now distinguishes constant inputs from failed
  arithmetic. Exact zero variance maps to zero; a non-finite variance,
  covariance, denominator, Pearson value, or R2 value remains NaN and is
  excluded from primary-score ranking on CUDA, ROCm, and Metal.
- CUDA, ROCm, and Metal record conservative base-two magnitude bounds during
  matrix upload. Exponent-risky descriptor chunks use three-pass
  scale-normalized covariance, while ordinary chunks retain their established
  two-pass or cached-statistics path. Positive scaling does not change the
  Pearson or R2 definition.
- CUDA and ROCm payloads can compile one mutual-information arithmetic policy:
  `fast` or `fp64`. Standard distribution payloads remain `fast`; local fp64
  payloads promote contribution evaluation, logarithms, reduction,
  finite-sample correction, and normalization before the final fp32 result
  cast.
- `EngineConfig` and backend diagnostics expose a precision contract that
  separates matrix storage from compute policy. The executable public pair is
  currently `float32 + stable`; unsupported `float64`, `exact`, and
  guard-disabling `fast` requests fail before input coercion or execution.
- Capabilities report interaction, accumulator, and result widths per metric.
  In particular, CUDA and ROCm MI width comes from the loaded payload flag
  instead of being inferred from the backend name.
- ROCm payload staging now requires the explicit immutable `bundled` wheel
  policy. The candidate wheel records pinned ROCm 7.2.3 inputs, GFX targets,
  component versions and licenses, driver compatibility sources, size limits,
  and unsupported mixed-runtime coexistence.
- ROCm release validation checks the actual ELF closure, relative RPATH and
  SONAME state, CycloneDX SBOM coverage, per-component ownership and size, and
  clean installed resolution without `/opt/rocm` userspace.
- The GPU-enabled architecture gate runs the integrated Rust workspace with one
  test thread. This prevents concurrent-context contention on the validated
  integrated ROCm host while preserving parallel focused-package tests.

## Distribution Policy

The standard release remains the 11-artifact RT-off bundle:

- six Core artifacts;
- two CUDA wheels plus one CUDA source distribution;
- one ROCm wheel plus one ROCm source distribution.

The optional OptiX `gafime-cuda-rt` artifacts remain a separate non-PyPI lane.
The standard CUDA and ROCm payloads retain fp32 MI arithmetic and do not carry
both precision variants.

## Deliberate Non-Claims

- This release does not provide an end-to-end fp64 matrix pipeline. Matrix
  ingest, storage, interaction products, and result tables remain fp32.
- Metal does not provide fp64 arithmetic because Metal Shading Language has no
  fp64 type.
- ROCm `system` and `amd-wheels` policies are not implemented. Loading the
  bundled ROCm userspace in a process that already owns another ROCm userspace
  remains unsupported.
- Scale-normalized covariance cannot recover an interaction product that
  overflowed before normalization.
- This release does not implement the post-1.0 ranking, pairwise GEMM, or
  out-of-fold discovery design track.
- No performance improvement is claimed for the numerical hardening. The
  ordinary-range fast path is retained, and fp64 MI remains opt-in because its
  cost is hardware and histogram-shape dependent.

## Evidence Boundaries

- Numerical runtime evidence covers local `sm89` CUDA and local `gfx1150` ROCm;
  hosted Apple hardware validates the Metal payload and public API path.
- Other packaged GPU architectures are compile coverage, not runtime evidence.
- The ROCm wheel policy report is packaging and dependency evidence, not a
  legal opinion or a mixed-runtime compatibility proof.
- Publication requires a fresh candidate-commit run of all publication-disabled
  workflows and collision checks against live PyPI.

## Release Validation

The selected release commit must pass the complete publication-disabled wheel
workflow, native-platform workflow, v1 contract workflow, installed-wheel
contracts, and applicable CUDA, ROCm, and Metal parity gates. The ROCm lane must
also emit and validate `rocm-wheel-policy-report.json`.

The exact validation, publication, and recovery commands are maintained in
[`release-operations.md`](release-operations.md). This note does not authorize
a tag or upload; publication requires explicit maintainer approval from the
final reviewed commit.
