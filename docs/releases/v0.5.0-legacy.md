# GAFIME v0.5.0-legacy Release Notes

v0.5.0-legacy is a GitHub-only checkpoint release for the v0.5 development
line. It is not a PyPI distribution release and it is not the forward
architecture for GAFIME.

This tag exists to preserve the work, measurements, and hard lessons from the
v0.5 cycle before the project moves to the Rust-owned orchestration rewrite.
The v0.5 line produced valuable implementation pieces, but it also proved that
the current layered engine cannot remove end-to-end overhead without a deeper
restructure.

## Release Status

- Release name: `v0.5.0-legacy`
- Distribution target: GitHub tag and documentation only
- PyPI status: not published
- Workflow status: no GitHub release or wheel workflow is intentionally
  triggered by this documentation branch
- Support status: legacy checkpoint, deprecated as the long-term architecture

Use this release when you want to inspect or locally reproduce the v0.5 work.
Use the future v1.x line for the production architecture direction.

## What We Worked On

The v0.5 cycle focused on reducing orchestration overhead and preparing GAFIME
for resident execution, native planning, native result handling, export handles,
and graph capture.

Major work areas:

- `gafime.compile` API surface:
  - `CompileFlags(plan=True, graph=False, export=False)`
  - `CompiledGafime`
  - `gafime.compile(...)`
  - `GafimeEngine.compile(...)`
- Rust-first scenario planning through `gafime/compile/RustCompileSrc/` and the
  existing PyO3 `gafime_cpu` crate.
- Compact scenario descriptors for continuous, discrete-era, and time-series
  planning.
- Power-user candidate counting for wide scenario plans, including explicit
  `max_feature_candidate=-1` behavior and a safety cap for unknown/unbounded
  requests.
- Resident compiled sessions, especially continuous matrix residency and
  time-series metric cache reuse.
- Native framework export protocols on native buffers.
- CUDA and HIP graph primitives for resident continuous matrix sessions.
- Metal graph evaluation, with v0.5 keeping graph mode unsupported rather than
  shipping an unvalidated Metal command-buffer reuse path.
- Decision-path staging as the replacement direction for the old discrete
  candidate family.
- GPU discrete candidate purge, so branch-heavy discrete candidate handling does
  not remain in GPU kernels.
- Release measurement scripts under `tests/release_measure/` for compile,
  export, graph, backend parity, decision-path lift, and telemetry.
- ROCm safety work for gfx1150 host-mapped input behavior.
- Compact native report metadata storage to reduce repeated string/object churn.

## What We Found

The v0.5 work answered several important questions.

### Compile Works As An API, But Not As Enough Of An Ownership Boundary

The compiled artifact can exist and can route through reusable sessions. The
problem is that the old engine still owns too much of the execution flow. The
compiled path was layered on top of `GafimeEngine` instead of replacing the
engine's plan-execute-reduce loop.

That means v0.5 improves pieces of the pipeline, but it does not fully remove
Python from orchestration.

### Graph Capture Was Real, But At The Wrong Granularity

CUDA graph support captured and replayed fixed-shape resident launches. HIP had
matching primitives. This was not fake bookkeeping.

The measured problem was granularity. Per-call graph replay still paid host
sync, descriptor copy, result copy, and Python/session-loop overhead. On the
observed RTX 4060 path, graph replay was not a net win at the current call
boundary, and one measured large path was about `0.715x` versus normal launch.

The useful graph target is larger:

- keep matrix and target resident
- run the multi-arity sweep inside the native host loop
- rank/compare natively
- replay once per permutation with one synchronization point

That shape belongs in a Rust-owned orchestrator plus native GPU host code, not
in a Python loop that calls one shape at a time.

### Result Materialization Was A Scale Wall

The native result record design was too heavy for very large runs because it
stored repeated strings and Python objects per record. A rough 10 million
record path would become memory-bound before the compute path could matter.

The local final v0.5 fix compacted repeated native report metadata, but the
complete solution is a compact native `ResultTable` owned below Python, with
Python exposing views rather than materializing every record.

### Discrete Candidates Were The Wrong GPU Shape

The old discrete candidate family mixed heterogeneous candidate types and
branch-heavy behavior. That does not match the clean arity-aware continuous
kernel shape, where homogeneous launch groups stay compute-bound.

The v0.5 direction removed GPU discrete candidate handling and shifted the
feature-family direction toward native decision-path split finding. This is a
structural replacement, not a temporary GPU fallback.

### Rust Planning Was The Right Direction

The Python planner was useful for bootstrapping, but it should not be the owner
of candidate counting, chunking, launch protocol emission, or result reduction.
The Rust `gafime_cpu`/PyO3 path proved that first-class Rust planning fits the
project. The next line should move all general orchestration into Rust, not only
the planner.

## Limitations We Hit

v0.5.0-legacy should be treated as a checkpoint because these limitations are
architectural, not small bug fixes:

- Python still participates in orchestration loops.
- The engine and compile artifact still have circular ownership in the v0.5
  structure.
- Planning is still split across multiple homes instead of one Rust
  orchestrator.
- There are still multiple Python-to-native boundaries: pybind11, PyO3, and
  ctypes-style backend surfaces.
- GPU graph capture is per-shape, not whole-sweep/permutation.
- Ranking and result reduction are not fully below Python.
- The v0.5 release measurement suite exists, but the final OpenML tour and deep
  telemetry matrix are intended to be run against the merged integration branch
  and cited from logged artifacts only.
- Metal graph support remains deferred.
- The old engine layout makes more feature work risky because every new family
  tends to add another branch inside the same monolithic flow.

## Why v0.5.0 Was Deprecated

v0.5.0 was deprecated because the project goal changed from "add a compile
artifact on top of the existing engine" to "make Rust the ownership spine of the
engine."

The old direction could keep adding sessions, flags, graph wrappers, and export
objects. That would not solve the root problem: GAFIME needs one directional
pipeline:

```text
Python API -> Rust orchestrator -> CPU Rust engines / GPU native host+device
```

The future architecture should make Python thin, move plan/schedule/reduce into
Rust, move CPU SIMD into Rust, and keep GPU code in vendor-specific native
device/host/tune modules. That is a major-line change, not a v0.5 patch.

## Milestones Hit

The v0.5 cycle still produced real milestones:

- Public compile API skeleton exists.
- Rust-backed scenario planning exists and Python can act as a thin adapter for
  that planning stage.
- Power-user planning semantics exist for wide candidate counts.
- Resident continuous sessions exist.
- Time-series metric cache/residency work produced major local speedups on the
  time-series completion path.
- Framework export protocols were implemented and validated for native buffers.
- CUDA graph primitives exist and passed parity checks.
- HIP graph primitives were mirrored where device-copy mode is available.
- ROCm gfx1150 host-mapped safety was fixed.

## How To Use v0.5.0-legacy Locally

This is a source checkout workflow. It is not a PyPI install target.

```bash
git clone https://github.com/onlyxItachi/GAFIME.git
cd GAFIME
git checkout v0.5.0-legacy

python3 -m venv .venv
. .venv/bin/activate
python -m pip install -U pip setuptools wheel
python -m pip install -e .
python setup.py build_ext --inplace
python -m unittest discover tests
```

Rust planner/helper validation:

```bash
PYO3_USE_ABI3_FORWARD_COMPATIBILITY=1 \
  cargo test --manifest-path src/cpu/gafime_cpu/Cargo.toml
```

ROCm local smoke, when ROCm is installed and the user is in the correct render
group:

```bash
LD_LIBRARY_PATH=/opt/rocm/lib PYTHONPATH=. \
  python -m unittest tests.test_rocm_native_backend
```

CUDA validation requires a CUDA payload-capable local build and NVIDIA hardware.
The v0.4.7 split-payload policy still applies: base `gafime` should not carry
CUDA or ROCm payload binaries.

## Why The Branchy Workflow Happened

v0.5 needed branchy development because the work mixed three risk profiles:

- release-safe integration changes
- high-risk GPU kernel experiments
- architecture-discovery work that changed the next major design

Keeping those on separate branches prevented experimental kernel changes and
graph/autotune attempts from blocking the cleaner integration line. It also
made rollback easier when the direction changed from "ship v0.5 as the new
compile architecture" to "preserve v0.5 as a legacy checkpoint and rewrite the
ownership model."

This is not intended to be the normal release workflow. Future major work should
freeze contracts first, then land in smaller phase branches with golden parity
checks after every phase.

## Future Of GAFIME: v1.x And Beyond

The next architecture should be a major-line rewrite with Rust as the ownership
spine:

- Python becomes a thin API/report view layer.
- Rust owns plan, schedule, residency policy, backend dispatch, reduction, and
  compact result tables.
- CPU SIMD engines move into Rust with runtime ISA dispatch.
- GPU remains vendor-native, split into device, host, and tune modules for CUDA,
  HIP/ROCm, and Metal.
- GPU host code owns resident buffers, graph capture/replay, ranking, and the
  native execution loop.
- The Rust-to-GPU boundary is a stable C ABI around a `LaunchProtocol` and
  compact `ResultTable`.
- Golden-output parity is frozen before each rewrite phase.
- Deep telemetry explicitly tracks end-to-end time, GAFIME native time,
  downstream model-fitting time, data-transfer overhead, and Python/GIL
  communication overhead.

The v0.5 work is valuable because it exposed the exact boundaries that must move.
The v1.x work should not continue layering more orchestration on top of the old
engine. It should replace the ownership structure.
