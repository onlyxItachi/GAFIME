# GAFIME v0.5.0-legacy Release Notes

> A legacy checkpoint for the v0.5 compile/orchestration work. Not a PyPI
> release. Not the future architecture. Very much worth preserving.

v0.5.0-legacy exists to honor the v0.5 cycle: the compile API, Rust planning
work, resident sessions, graph experiments, export handles, decision-path
staging, ROCm fixes, measurement scripts, and the architectural lessons that
changed the direction of the project.

It is a GitHub-only checkpoint. The purpose is to keep the work inspectable,
buildable, and historically clear before GAFIME moves toward the Rust-owned
orchestration rewrite.

## ✨ What v0.5 Worked On

The v0.5 cycle tried to reduce orchestration overhead and prepare GAFIME for a
compiled execution model:

- native scenario planning
- resident backend sessions
- native result/report tables
- export handles for downstream frameworks
- CUDA/HIP graph capture
- decision-path feature discovery
- telemetry and release measurement scripts

The release did not become the final architecture, but it did produce important
working pieces.

### Compile API

v0.5 introduced the public compile surface:

- `CompileFlags(plan=True, graph=False, export=False)`
- `CompiledGafime`
- `gafime.compile(...)`
- `GafimeEngine.compile(...)`

This gave GAFIME an artifact-shaped API: something that can own planning,
sessions, warnings, backend handles, and repeated analysis runs.

### Rust-First Planning

The scenario planner moved in the right direction by using Rust as a first-class
planning layer through:

- `gafime/compile/RustCompileSrc/`
- `src/cpu/gafime_cpu/src/lib.rs`
- the existing PyO3 `gafime_cpu` extension loaded through `gafime.subfunctions`

Python became thinner in the planning path, with Rust handling compact scenario
counts and chunk descriptors where available.

### Power-User Planning

v0.5 added wide-count planning behavior:

- explicit `max_feature_candidate=-1` power-user mode
- wide candidate counts for known/explicit caps
- practical safety caps and warnings for unknown unbounded requests
- saturating-count semantics so large plans do not require full materialization

This matters because GAFIME should be able to describe huge search spaces
without allocating huge Python lists.

### Resident Sessions

The compiled session work moved backends toward persistent native state:

- continuous matrix residency
- reusable backend sessions
- time-series metric cache reuse
- reduced repeated upload/allocation pressure

This was one of the strongest v0.5 signals: repeated analysis should reuse
native state instead of rebuilding it from Python every time.

### Export Handles

The native export work added framework-facing buffer protocols for future
integration:

- native buffer ownership
- result/export handle lifetimes
- NumPy/Torch DLPack validation
- zero-copy direction for downstream model workflows

This was not a public XGBoost promise yet. It was a stable internal bridge for
tests and future framework integration.

### Graph Capture

CUDA graph primitives were implemented and validated for fixed-shape resident
continuous launches. HIP mirrored the same direction where device-copy mode is
available.

Metal was evaluated and intentionally left unsupported for graph mode in v0.5,
because Metal's command-buffer/ICB model needs separate validation rather than a
fake CUDA-like abstraction.

### Decision Path

v0.5 also began replacing the old discrete candidate family with native
decision-path split finding:

- whole-data native split finder
- depth-k greedy recursion
- residual boosting
- release wiring
- split caps and measurement scripts

This became the cleaner direction for branchy feature discovery.

## 🔬 What We Found

v0.5 answered hard questions. Some answers were uncomfortable, but they were
useful.

### 1. Compile Worked, But The Boundary Was Too High

The compile artifact exists. It can plan, hold flags, route sessions, and run
analysis.

The problem is ownership. The old `GafimeEngine` still owns too much of the
actual plan-execute-reduce flow. v0.5 layered compile on top of the engine
instead of moving orchestration below Python.

That means v0.5 improved the shape, but it did not fully remove interpreter and
session-loop overhead.

### 2. Graph Capture Was Real, But Too Small

The graph work was not fake. CUDA captured and replayed fixed-shape resident
launches. HIP had matching primitives.

The measured issue was granularity. Per-call graph replay still paid for:

- host synchronization
- descriptor copies
- result copies
- Python/session-loop dispatch

On the observed RTX 4060 path, graph replay was not a net win at the current
boundary. One measured large path was about `0.715x` versus normal launch.

The useful target is bigger:

```text
resident matrix + resident target
multi-arity native sweep
native rank/compare
one graph replay per permutation
one synchronization point
```

That belongs in native GPU host code driven by a Rust orchestrator.

### 3. Result Materialization Was A Scale Wall

The native report record was too heavy for large candidate counts because
strings and Python objects appeared at record granularity.

The final local v0.5 checkpoint compacted repeated native report metadata, but
the complete answer is a compact native `ResultTable` with Python exposing views
instead of materializing every record.

### 4. Discrete GPU Candidates Were The Wrong Shape

The old discrete candidate path mixed heterogeneous candidate types and
branch-heavy logic.

That is the opposite of the continuous kernel shape that works well: homogeneous
arity-aware launches, predictable register use, and compute-bound execution.

v0.5 therefore purged GPU discrete candidate handling and moved the feature
family direction toward native decision-path split finding.

### 5. Rust Should Own More Than Planning

Rust planning was the correct direction, but it should not stop there.

The next line should make Rust the ownership spine for:

- plan
- schedule
- residency policy
- backend dispatch
- reduction
- compact result tables

Python should become the API and report-view layer, not the loop owner.

## ⚠️ Limitations

v0.5.0-legacy is deprecated as the long-term path because these limits are
structural:

- Python still participates in orchestration loops.
- The engine and compile artifact still have circular ownership.
- Planning is still split across multiple homes.
- The codebase still has multiple Python-native boundaries: pybind11, PyO3, and
  ctypes-style backend surfaces.
- GPU graph capture is per shape, not whole sweep/permutation.
- Ranking and result reduction are not fully below Python.
- The final OpenML tour and deep telemetry matrix must still be produced from
  logged `tests/release_measure/` artifacts.
- Metal graph mode remains deferred.
- Adding feature families to the old engine layout keeps increasing coupling.

These are not reasons to discard the work. They are the reasons the next
architecture needs a stronger ownership model.

## 🧭 Why v0.5.0 Was Deprecated

The project goal changed.

The old goal was:

```text
add a compile artifact on top of the current engine
```

The new goal is:

```text
Python API -> Rust orchestrator -> CPU Rust engines / GPU native host+device
```

That is a major architectural change. It cannot be achieved cleanly by adding
more flags, sessions, graph wrappers, or export objects to the old engine.

v0.5 is therefore preserved as a legacy checkpoint, while the forward path moves
to the v1.x rewrite.

## 🏁 Milestones Hit

v0.5 still landed real milestones:

- compile API skeleton
- Rust-backed scenario planning
- power-user wide-count planning
- resident continuous sessions
- time-series metric-cache/residency acceleration
- framework-grade native export protocols
- CUDA graph primitives with parity checks
- HIP graph primitives where device-copy mode is available
- ROCm gfx1150 host-mapped safety fix
- GPU discrete candidate purge
- decision-path native split-finding staging
- release measurement suite
- compact native report metadata storage

This is enough to deserve a checkpoint tag. It is not enough to justify freezing

## 🧪 How To Use v0.5.0-legacy Locally

This is a source checkout workflow. It is not a PyPI install target.

```bash
git clone https://github.com/onlyxItachi/GAFIME.git
cd GAFIME
git checkout v0.5.0-legacy

python3 -m venv .venv
. .venv/bin/activate
python -m pip install -U pip setuptools wheel
python -m pip install -e .
python setup.py build_ext --inplace
python -m unittest discover tests
```

Rust planner/helper validation:

```bash
PYO3_USE_ABI3_FORWARD_COMPATIBILITY=1 \
  cargo test --manifest-path src/cpu/gafime_cpu/Cargo.toml
```

ROCm local smoke, when ROCm is installed and the user is in the correct render
group:

```bash
LD_LIBRARY_PATH=/opt/rocm/lib PYTHONPATH=. \
  python -m unittest tests.test_rocm_native_backend
```

CUDA validation requires a CUDA payload-capable local build and NVIDIA hardware.
The v0.4.7 split-payload policy still applies: base `gafime` should not carry
CUDA or ROCm payload binaries.

## 🌿 Why The Branchy Workflow Happened

v0.5 needed branchy development because the work mixed three different risk
profiles:

- release-safe integration work
- high-risk GPU kernel experiments
- architecture-discovery work that changed the next major design

Keeping those tracks separate prevented experimental kernel changes and
graph/autotune attempts from blocking the cleaner integration line. It also
made rollback easier when the project changed direction.

This is not meant to be the normal release workflow. Future major work should
freeze contracts first, then land through smaller phase branches with golden
parity checks after every phase.

## 🚀 Future Of GAFIME: v1.x And Beyond

The next architecture should be a major-line rewrite with Rust as the ownership
spine:

- Python becomes a thin API/report-view layer.
- Rust owns plan, schedule, residency policy, backend dispatch, reduction, and
  compact result tables.
- CPU SIMD engines move into Rust with runtime ISA dispatch.
- GPU stays vendor-native, split into device, host, and tune modules for CUDA,
  HIP/ROCm, and Metal.
- GPU host code owns resident buffers, graph capture/replay, ranking, and the
  native execution loop.
- The Rust-to-GPU boundary becomes a stable C ABI around a `LaunchProtocol` and
  compact `ResultTable`.
- Golden-output parity is frozen before each rewrite phase.
- Deep telemetry tracks end-to-end time, GAFIME native time, downstream model
  fitting time, data-transfer overhead, and Python/GIL communication overhead.

v0.5 matters because it exposed the exact boundaries that must move. v1.x should
not keep layering orchestration over the old engine; it should replace the
ownership structure.
