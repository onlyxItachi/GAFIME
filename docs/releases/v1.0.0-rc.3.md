# GAFIME v1.0.0-rc.3 — Native File Acquisition And Release Hardening

RC3 stabilizes the established GAFIME v1 runtime after public file ingestion
exposed a boundary-cost gap. Repository/Cargo identity: `1.0.0-rc.3`;
canonical tag and GitHub Release identity: `v1.0.0-rc.3`; Python/PyPI identity:
`1.0.0rc3`. Preparation is not publication authority. Operational gates and
live publication state are routed through [STATUS.md](STATUS.md) and the
canonical public channels.

## Changes Since RC2

- Ordinary numeric `dataload`, including default and fully configured analysis,
  acquires projected Polars data through incremental Arrow C Streams into
  checked Rust-owned input. Acquisition feeds the existing planner/executor;
  it is not a restricted alternative execution policy. Whole-dataset Python
  row/scalar materialization and byte staging are no longer the numeric file
  path.
- Multiple batches, slices and differently chunked feature/target streams retain
  alignment and exactly-once foreign-owner release. Checked capacity hints do
  not replace actual batch/end-of-stream validation. Loader-only foreign frames
  release before resident compilation; acquired buffers transfer ownership.
- File ingestion preserves requested seeds, precision, metrics, significance,
  generated families and backend policy. Finite fp32 range overflow is rejected
  before narrowing, while source NaN/Inf retain their distinct semantics.
  Literal feature/target names cannot become wildcard or regular expressions.
  Candidate-cap warnings remain visible.
- Target-dependent time-series screening is repeated for permutations and
  compiled target/reseed changes, rather than reusing a shortlist selected
  against an earlier target. Decision-path rebuild failure cannot retain a
  partially updated adaptive state.
- Ordinary exported CUDA/HIP ABI 1.0 and ABI 1.1 entry points serialize through
  one nonrecursive gate per loaded payload instance, covering device selection,
  runtime work, cleanup and caller-device restoration. This does not provide
  multi-call handle-lifetime atomicity or coordinate foreign frameworks,
  separately loaded payloads or experimental RT entry points.
- Bounded configuration validation rejects invalid thresholds and negative
  counts, normalizes backend-name case and reports mutually exclusive generated
  families clearly. Documented compatibility no-ops remain unchanged.
- Development and release policy now require affected-component and public
  end-to-end evidence: fast resident execution alone does not prove fast
  ingestion. Installed-wheel numerical/error comparisons, fresh-process RSS,
  latency, copy/lifetime accounting and complete environment provenance remain
  independent gates.

The [ingestion hardening plan](../rc3-ingestion-hardening.md),
[cost policy](../ingestion-rss-policy.md) and
[bounded Polars investigation](../evidence/rc3-polars-rss-comparison.md)
describe the implementation and evidence limits. Parser-aware RSS controls are
independent of GAFIME acquisition/execution and must pass their own original
ceilings before supplying a baseline. Numeric allowances and latency limits
remain unchanged; historical failed verdicts are retained. No Polars downgrade,
production allocator override, forced trim or weaker ownership was introduced.

## Runtime And Distribution Contract

Python remains the public declaration/reporting boundary. Rust owns validation,
planning, lifecycle, backend selection and candidate-level Rayon execution with
worker-local scratch and per-candidate SIMD/native arithmetic. CUDA, ROCm/HIP
and Metal own their native device execution. ABI 1.0 stays frozen; ABI 1.1 stays
the generic typed-buffer/numeric-route boundary with additive compatibility
fixtures. No new public API, feature family or backend is introduced by RC3
release preparation.

Core (`gafime`) has no vendor-payload dependency. CUDA (`gafime-cuda`) and ROCm
(`gafime-rocm`) require exactly matching Core. Dedicated CPython 3.10–3.14
wheels and platform coverage remain derived from the release manifest. CUDA
requires the system runtime. ROCm remains thin/system-runtime, with truthful
raw Linux wheels on GitHub and its matching source distribution on PyPI.
Metal is embedded only in macOS arm64 Core; no standalone Metal distribution
exists. RT/OptiX remains experimental, local-only and excluded from release
artifacts.

Under the manifest's CPython matrix, Windows ARM64 contributes
five dedicated wheels, including CPython 3.10, provisioned from official
`pythonarm64` NuGet packages.
Polars remains `polars>=1.3,<2`; the Polars 2 migration and broader combined
streaming/borrowed-input architecture are separate post-v1 work.

## Precision Profiles

`EngineConfig(precision=...)` remains the only public precision selector.
`fp32` is genuine lane-wide fp32 for ingest/storage, pointwise arithmetic,
reductions/statistics, ranking and public results. Default `mixed` uses fp32
ingest/storage and pointwise arithmetic with fp64 statistics, ranking and
public results. `fp64` remains end-to-end fp64 without an fp32 intermediate.
Core, CUDA and ROCm carry all three profiles. Embedded Metal supports fp32 only;
explicit mixed/fp64 requests fail closed. No precision-specific package or
wheel family is added.

The [authoritative v1 API reference](../notebooks/gafime_v1_api_reference.ipynb)
and [public API coverage](../public-api-coverage.md) remain the supported API
and lifecycle reference. Analysis still holds the Python GIL; other Python
threads and Ctrl-C handling can wait for native return. This release does not
introduce detachment or cancellation; see the
[execution lifecycle guide](../eager-resident-compiled-execution.md).

## Qualification And Claim Boundaries

Fix tests, matched diagnostic controls and prior-source review establish
bounded engineering evidence, not approval of final RC3 artifacts. Publication
requires exact-candidate standard security qualification, hosted checks,
installed public-workflow evidence, an eligible exact-release-tip build,
independent frozen-bundle provenance/checksum/composition verification and
exact-artifact Core/CUDA/ROCm/Metal execution under
[release operations](release-operations.md).

The protected candidate must be settled, qualified, locked and admitted
unchanged to `main` before canonical tagging and official frozen publication.
Published RC2 and the earlier unpublished stable candidate are not RC3 artifact
sources. The established [security policy](../../SECURITY.md) and historical
[pre-RC baseline](../security/pre-rc-baseline.md) remain in force; earlier
standard/deep scan records do not qualify a later exact source. Detailed
finding material stays private, and no security guarantee is claimed.

## Version Identity

Semantic Versioning governs repository/Cargo `1.0.0-rc.3` and canonical
Git/GitHub `v1.0.0-rc.3`; PEP 440 governs Python/PyPI `1.0.0rc3`. The release
parser enforces the mapping across source metadata and frozen artifacts.
Historical compact tags and release records remain unchanged. The mixed naming
in `docs/releases/` is intentional historical preservation; new identities
use canonical SemVer spelling.

## Deliberate Non-Claims

- Scale-normalized covariance cannot recover a product that overflowed before normalization.
- A checked owned snapshot is not an atomic transaction with external writers.
- Arrow acquisition is not resident zero-copy; required layout conversion and
  allocator-retained pages are disclosed, not hidden or treated as exact live
  allocation counts.
- Workload/host-specific measurements do not establish universal throughput or
  comparative GPU speedups. Issue #71 remains separate permanent benchmark work.
- Hosted compilation is not physical CUDA/ROCm execution evidence; earlier
  physical records do not automatically qualify changed frozen artifacts.
- Security review does not establish vulnerability-free or fully secure code.
- RT/OptiX, Polars 2, GIL detachment and future feature/compiler architecture
  are not distributed RC3 capabilities. Stable qualification remains separate.
